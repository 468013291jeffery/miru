## 一、先确定交哪一种稿

| 交付形态 | 写法与用途 | 不要混用的规则 |
|---|---|---|
| 当前中文编剧稿 | 用本规范的 `【栏目名】`，规则解析为 `bible.json`，角色围绕场景自由表演 | 不要求每章硬塞 `# CHOICE`，不把全部台词逐字锁死 |
| 已有故事圣经 | 直接编辑 `bible.json`；字段对照见第十七节 | 不把自造字段当成引擎已支持能力 |
| 旧逐字剧 DSL | 用 `# CHAPTER`、`# SCENE`、台词、标签；见第十八节及 [parser.md](parser.md) | 旧播放批次、暂停和章末选择要求只适用于这条入口 |

**新写或升级自由故事，优先按中文栏目交稿。** 一章对应一级剧情与关系台阶；作者规定事实、人物和可发生的变化，智能体接住玩家当下的参与，再在合法范围内表演。作者不能用大纲替玩家确认恋爱、原谅、亲密或行动成功。

[终版总规则](../source/src/rules_final.md)中已确认的长篇项目仍按 15—20 章、普通完整路线 24 小时以上有效游玩规划。本文两章样稿仅用于演示交稿语法，不代表达到内容容量；轮数和估算时长也不等于实际游玩时长。

## 二、交稿文件与写作顺序

中文稿分五部分：作品设定 → 人物小传 → 分章大纲 → 结局 → 图片和开场视频。分部标题可写成“第一部分 作品设定”；栏目名必须照模板，不能改成近义词。

创作顺序仍是：体验承诺与身份边界 → 世界和人物 → 结局方向 → 阶段主干 → 认知、情绪和反转链 → 选择与后果 → 场景 → 对白。修订人物秘密时，要联动开局认知、事件、揭晓节点和相关台词，不能只改人物卡一处。

| 文件 | 内容 |
|---|---|
| `作品中文稿.txt` | 仅包含能解析的中文栏目和内容 |
| `创作说明.md` | 路线图、选择契约、状态规划、待确认项、翻译说明和能力接入要求 |
| `bible.json` | 中文稿转换结果或经接入人员确认的直接数据稿 |
| 素材清单及文件 | 封面、人物图、场景图、高光图、照片、视频与槽位映射 |

不要把编辑批注、验收记录或后端配置粘进导语、台词或旧逐字剧正文。中文稿不认识的栏目会报错；例如 `【章节目标】` 应改为 `【本章目标】`。目前不能自行增加 `【旁白】`、`【感官】`、`【上下文】`、`【升级台阶】`。

## 三、作品设定怎么写

| 栏目 | 写法与用途 |
|---|---|
| `【作品名】` | 明确作品标题，不加版本、编剧备注 |
| `【取向】` | 中文稿只写“男女”“男男”“女女”；与玩家和可发展关系角色的性别一致 |
| `【题材标签】` | 用顿号分隔，最多取 8 个，优先题材、关系和体验词 |
| `【一句话卖点】` | 玩家处境＋角色吸引点＋值得参与的问题；不要直接公布终局 |
| `【作品简介】` | 2—4 句说明身份、冲突、角色和可参与的方向 |
| `【故事背景】` | 玩家进场前要知道的定位和眼前处境，建议 400 字以内、少量短段 |
| `【世界规则】` | 能力、资源、组织规则、限制、代价和时间如何推进 |
| `【演出风格】` | 如何回应、如何分配发言、怎样写动作与台词、怎样推进 |
| `【相处规则】` | 拒绝、朋友边界、角色自主性、现实离线与剧情边界 |
| `【玩家身份】` | 按下例写性别、身份，可补处境和玩家本人知道的隐情 |
| `【核心问题】` | 全剧持续追问的事件或关系问题；不要写标准答案 |
| `【每章节奏】` | 使用固定句式，数字按作品调整；见第九节 |

`【故事背景】` 给玩家读，`【世界规则】` 和 `【演出风格】` 参与智能体提示。后两栏也不能成为所有角色共享的秘密仓库；角色私密事实放在该角色小传中，后章揭晓不要写进公共开场。

```text
【玩家身份】性别：女 身份：来取寄存画的成年客人 处境：画框上的编号与你的凭条不同 藏着的事：你认得凭条上的笔迹
【核心问题】画为什么被换了框，你愿意和谁一起查清？
【每章节奏】最少聊 12 轮，聊满 18 轮一定给换章按钮
```

“藏着的事”会显示在玩家的故事背景卡上，应写**玩家本人已知、其他人未必知道**的内容，不能放作者要向玩家保密的反转。

`【演出风格】` 要写可执行的规则：

```text
先回答玩家最新一句。被点名的人先回，其他人只有新信息、不同意见或具体请求时再接。
动作写可观察的行为，台词用人物自己的短句；不要人人轮流发表同样的关心。
当前话题暂告一段落时，用已写出的线索、邀请或事件推进一步。
不要提前演下一章，不替玩家行动，不把尚未完成的承诺当成事实。
```

`【相处规则】` 则写持续边界：

```text
玩家说只做朋友、不要追求或不想亲近时，立即停止对应追求，后续章节继续遵守。
角色可以主动邀请、拒绝和表达失望，但不能拿危险、内疚或离线惩罚逼玩家答应。
拒绝游戏、照片或亲密邀请仍有有效参与空间；不靠这些行为阻断核心线索。
```

## 四、人物小传怎么写

每个角色从 `【全名】` 开始，后面的栏目只属于此人。中文稿按人物顺序生成 `c01`、`c02` 等 key；已经上线的作品不要随意重排人物再覆盖，否则素材和角色引用会变。

| 栏目 | 应写什么 |
|---|---|
| `【全名】`／`【常用称呼】` | 全名与常用简称，不能与其他人物冲突 |
| `【性别】`／`【年龄】` | 男或女；数字年龄，所有角色必须成年 |
| `【人物定位】`／`【能否发展感情】` | 主角或次要角色；能或不能 |
| `【身份】` | 社会身份、能力范围、与当前事件的关系 |
| `【外貌和习惯】` | 稳定外貌、服装锚点、具体习惯，便于跨图保持一致 |
| `【说话方式】` | 句长、用词、节奏、压力下怎样改变 |
| `【性格】` | 欲望、价值排序、矛盾与压力反应；重要内容前置，建议不超过 600 字 |
| `【想要】`／`【害怕】` | 当前主动目标及其代价；不要只写“得到玩家／失去玩家” |
| `【底线】` | 不会做什么、被越界怎样拒绝、怎样可能修复 |
| `【对玩家的初始态度】` | 初识、旧识、戒备或已有关系的具体依据 |
| `【吸引力】` | 用行为让玩家看见的魅力，建议不超过 500 字 |
| `【开局认知】` | 已知／未知／怀疑及其来源，关键内容放前 160 字 |
| `【样例台词】` | 逐行写，建议 5 句、每句 45 字以内，体现不同情境 |
| `【秘密】` | 本人的固定隐情；需要条件揭露时用下一节的可解锁秘密 |
| `【人设类型】` | 一句概括反差来源，不能代替性格和行为 |
| `【嘴上和心里】` | 本人表达与真实诉求的差异，不等于别人能读心 |
| `【怎么调情】`／`【怎么吃醋】` | 触发情境、具体表达、被拒绝后如何收住 |
| `【玩家提要求时】` | 愿意、犹豫、拒绝各怎样表现，不写一律答应 |
| `【怎么看其他人】` | 每行“角色名：自己的态度”，名字需对应人物小传 |
| `【会怎么变】` | 长期变化的方向、必要经历和仍保留的特征 |

基础身份、性格、目标、底线、初始态度、吸引力和开局认知等是解析必需项；后面的鲜明人设与成长栏目应尽量补全，不能用“温柔、霸道、腹黑”几个词代替。

差的写法：“冷酷但温柔，很爱玩家，会保护她。”

可用的写法：

```text
【性格】遇到危险先安排退路，常忘了先问别人的意愿。被当面指出时会停住并解释，不迁怒。害怕再次做错决定，所以过度准备。
【对玩家的初始态度】第一次见面，对她的凭条存疑，仍先替她保管好被雨淋湿的画袋。
【怎么吃醋】话少一点，承认自己想留下；玩家选了别人就退开，不把选择变成争吵。
【会怎么变】从替人安排，到先询问再协助。转变需要玩家指出问题、他尝试放手，以及一次尊重不同选择的行为证明。
【开局认知】知道玩家来取画，见过原来的画框；不知道玩家认得凭条笔迹，只怀疑换框与旧仓库有关。
```

样例台词是声线参考，不是每轮照念的固定台词。人物成长是待发生的方向，不能在开篇就写成“他已经完全学会尊重所有选择”。

## 五、秘密和认知边界怎么写

秘密每条占一行，内部用中文分号分隔：

```text
【可解锁秘密】
秘密名：旧画框；内容：三年前他曾自费修过这幅画；从第几章起：2；好感到：开始在意；说出口的样子：先放下工具，再解释为何没留下名字
```

当前稳妥写法是四个中文好感阶段：**有点好奇（12）、开始在意（30）、心动（55）、深深在意（80）**。不要在中文稿这里直接写数字或自造“完全信任”等阶段；当前解析有两套秘密数据生成，数字并不能同时通过两套校验。

章数与好感条件都满足，表示**可以在适合的情境自然揭露**，不表示刚进章就自动公开。写清：

- 谁知道：秘密属于哪个角色；其他角色没有听到就不知道。
- 怎样被追问：未到条件时可坦承暂不愿说，不强迫角色编假答案。
- 怎样说出口：具体停顿、动作和措辞，不写玩家必然感动或原谅。
- 揭晓后能做什么：核对、追问、拒绝、保留判断，后文怎样读取。

核心事件的必要真相不能只靠恋爱好感解锁；要另写证据或调查的有效路径。秘密标题也不要直接写最终谜底，避免标题本身泄密。

固定隐情和可解锁秘密若描述同一件事，内容与保密条件必须一致；不要在 `【开局认知】`、公共世界规则或开场导语里又给所有人写一遍答案。

旧版推荐的 `card98` 不是当前这条故事引擎的认知入口。现在用人物 `knows`、本人秘密、各自 `actor_payload` 以及实际见闻分配信息；不要只交一个 `card98` 并期待它自动生效。完整“谁知道什么”的设计表可放创作说明，接入时逐项映射，不能仅存成无人读取的字段。

## 六、章节卡与场景的顺序

```text
【章序】第一章
【章名】闭馆前的一场雨
【时间】闭馆夜·九点
【地点】画廊·前厅
【在场人物】沈砚
【眼前的事】画框编号与你的凭条不同
【章节导语】雨声盖过音乐。沈砚把登记册摊在桌上，先等你看清画框上的编号。
【开场对白】
沈砚：编号不对。你想先看凭条，还是先看画？
【本章目标】让玩家获得一条可查证的线索，并决定是否继续了解沈砚。
【本章安排】……
【角色任务】
沈砚：……
【这一级的表现】
沈砚：……
【眼前邀请】……
【开场建议】
先看登记册
画框是什么时候换的？
我想先安静一下
```

**先写 `【地点】`，再写本章安排、角色任务、表现、音乐、游戏和事件。** 这些栏目会关联当前场景；先写场景栏目可能隐式创建场景。尤其“这一级的表现／本章音乐／小游戏／事件”同时写入章与场景，统一放在第一处地点之后，避免多出一场或缺地点。

同章第二次出现 `【地点】` 就开始下一场，需重新写该场的在场人物、本章安排、角色任务、眼前邀请和开场建议。“本章安排”虽然叫本章，实际属于当前场景。不要在每场重复同一个章级事件或小游戏栏目，以免覆盖章配置；复杂多场分配由接入人员核对转换结果。

章节卡只写当前公开内容：

| 栏目 | 写法 | 建议长度 |
|---|---|---|
| 章名 | 不重复写“第一章”，前端会加 | 16 字以内 |
| 时间／地点 | 只写内容，不再加“时间：”“地点：” | 各 18 字以内 |
| 在场人物 | 全名或常用称呼，用顿号分隔，只写有小传的人物 | 按实际场面 |
| 眼前的事 | 当前局势的一句话摘要 | 40 字以内 |
| 章节导语 | 已能看见、听见的画面，不能夹带后章答案 | 120 字以内 |
| 开场对白 | “角色名：台词”，只显示前两句，角色须在首场名单 | 每句 45 字以内 |
| 开场建议／选项文字 | 玩家能直接说或做的事 | 每条 30 字以内 |

这些字数多数是**样式建议和提醒**，不是统一截断或发布硬限。字段不要带 HTML、Markdown 标题、加粗或自带标签；短字段不要换行。不要为了缩短文字而漏掉关键事实。

`【本章目标】` 应写当前阶段可观察的改变，且不夹带不应提前透露的谜底。例如“能核对一条线索，并表明是否愿意继续同行”，不要写“玩家必须爱上他，下一章必须接吻”。

## 七、本章安排、角色任务和台阶表现分别写什么

| 栏目 | 核心问题 | 应包含的内容 |
|---|---|---|
| 本章安排 | 这场戏有哪些可发展的方向？ | 当前事实、矛盾或微张力、可用线索、玩家行动空间、可发生的后果和收束方向 |
| 角色任务 | 这个人此刻想做什么？ | 本人目标、知情依据、回应策略、不能越过的边界 |
| 这一级的表现 | 关系与局势目前到哪一步？ | 当前可表现的亲近、信任、坦白或冲突程度，尚不能提前到哪一步 |
| 会怎么变 | 整部作品中这个人如何成长？ | 长期方向与行为证明，属于人物小传 |

```text
【本章安排】已知：画框编号不同，登记册在桌上。玩家可问编号、查看凭条、请沈砚解释，也可暂不调查。若愿意核对，先比日期；若拒绝，保留登记册可稍后再查。这里只确认差异与调查方向，不揭晓换框者，不替玩家拆框。后续再次谈这幅画时，要接住玩家选择的调查方法。
【角色任务】
沈砚：先答编号问题；只知道自己三年前修画，不知道谁换框。需要触碰玩家物品时先询问。被拒绝后提供口头说明，不擅自拆开。
【这一级的表现】
沈砚：愿意解释专业事实，开始主动提供帮助；尚未坦白个人隐情，不以恋人身份要求玩家留下。
```

“本章安排”中的待发生内容必须写成条件或候选，不能写成已经完成的历史。角色任务按人单独分配，不要把甲的隐情粘在乙的任务里；也不要假设给导演的全局安排天然具有逐项保密能力。

重要选择要在创作说明中写清：入口、玩家意图、可见风险、即时反馈、影响什么、后文在哪里读取、能否改变主意、失败后怎样继续、汇合后保留什么。事件合作、关系选择、人物成长分别设计；一起查案不等于接受恋爱。

当前中文导入没有“任意状态规则自动执行”的通用语法。路线条件、道具消耗或复杂数值若未映射到已支持字段，只是创作设计；不能声称仅靠一句“特殊标记：证据+1”就已完成程序接入。

## 八、选项怎么写，后果算到哪一步

```text
【选项一】
选项文字：先核对登记册
选项后果：沈砚提供记录并解释核对方法；是否继续检查，由玩家下一步决定。
角色任务：沈砚：摊开日期页，不替玩家宣布查证成功。
特殊标记：无

【选项二】
选项文字：我们只做朋友
选项后果：沈砚接住边界，停止追求，保留正常聊天和调查空间。
角色任务：沈砚：明确答应，不用玩笑重启追求。
特殊标记：进入朋友模式
```

选项数字可用一、二、三等。每项至少写“选项文字”，建议同时写完整后果及各人任务。开场建议只是给玩家的表达入口，不等于有状态效果的正式选项。

当前中文特殊标记可识别：

- `特殊标记：进入朋友模式`：进入朋友模式，后章继续尊重边界。
- `特殊标记：直接进入结局：提前离开`：结局名必须与已写结局完全一致。
- `特殊标记：无`：普通选项，不写虚构的程序效果。

选择“愿意去”是意图或安排；到达地点才是到达事实。角色说“我会查”是承诺；查证回执出现后才算完成。文案必须保留“想、怀疑、打算、尝试、如果”的性质，不能把它们在后文回忆中一律改成既成事实。

## 九、推进、在场和长期相处

`最少聊 12 轮，聊满 18 轮一定给换章按钮` 是可解析句式；数字可调整，最少值不能大于目标值。这控制**推进按钮出现的机会**：达到条件后可以继续，玩家也可以留在当前场景聊天。多场章节的按钮可能先推进到下一场，不能把这两个数字理解为全章保证时长或到点自动换章。

作者应提供调查、共同活动、玩笑、休息、修复冲突和稳定关系中的具体内容。日常场面用新观察、小请求或共同完成的事保持变化，不靠固定轮数强制争吵。运行时会判断停滞并调度戏点，因此要准备符合本作基调的候选事件；“三轮没变化”不是作者必须每三轮制造危机的写作公式。

`【在场人物】` 是计划名单，实际名单会随离开、到达、跟随变化。导语不要无条件写“所有人一直跟着你”；没跟来的人不能听见私聊或下一场的秘密。再次出场要有可理解的来由。角色可以只回应被点名的问题，其他人没有新内容时不必插话。

玩家说“只做朋友”“别再追我”“我想独处”后，要在跨章安排、台词、照片邀请和结局里都保留其边界。现实离线不消耗剧情期限，不以催促登录或吃醋惩罚维持陪伴。

## 十、事件怎么写

```text
【事件】
门外传来两声门铃（触发：当前话题暂告一段落，且这次门铃尚未响过）
屋檐的雨声渐轻（触发：准备离开前厅，但玩家尚未决定是否出门）
```

每行一个候选事件。写清具体可听见或看见的变化和触发情境，不写“发生惊天反转”“突然很危险”这类空话。事件不能替玩家签约、接吻、打开物品或确认成功；不要借事件让不在场的人瞬间知道私聊内容。

当前调度有冷却和每章次数限制（至少间隔 8 轮、每章最多 2 次，默认每个事件一次）；事件池不是逐行必播清单。触发条件文字用于导演判断，并不等于逐字可执行的布尔表达式。必须严格执行的前置条件要另做已支持的数据接入，不能只靠描述保证。

## 十一、小游戏怎么写

```text
【小游戏】
用途：推进悬疑
玩法：找线索
出现时机：玩家愿意检查画框时，由沈砚先邀请；玩家未同意前不开始
赌注：一起找出画框的旧编号
赢了：发现旧日期，可以继续核对登记册
输了：只能认出一半编号，仍可从登记册继续查
不玩：沈砚尊重拒绝，提供改查登记册的办法
```

用途可写：推进悬疑、考验亲密、暧昧时刻、危机、较劲。玩法必须来自现有游戏库，可按库里的中文名或 id 写，例如“找线索”；不要自造玩法名并期待系统生成新游戏。

**赢了、输了、不玩都要写。** 三种结果分别带来什么新信息、关系反馈或替代方法，要与赌注对应；拒绝游戏不能成为死路。角色先邀请，游戏有结果后再接剧情，不能预写“你们刚才赢过一局”的共同记忆。告白、哭泣或冲突高潮时不要插入小游戏。作者场景回执流程只按真实 WIN／LOSE／SKIP 接剧情，失败与拒绝不扣好感。

当前导入同时兼容“找线索／真心话骰／赌一把／记旋律／默契考验／还原经过”的场景玩法，以及游戏库的章节邀请。不是所有名字都走同一条显示和结果流程。新稿每章先安排一个，接入时核对实际生成的场景或章节游戏和三种结果；旧 `⟦MG⟧` 属于另一入口。

当前官方故事不应依赖台词关键词自动触发游戏。不要仅写“戒指掉了”就当成已配置找戒指游戏。

## 十二、音乐与特效怎么写

```text
【本章音乐】悬疑
【环境氛围】下雨
【关键特效】
闪电：玩家抬头看向窗外，闪电确实照亮玻璃时
```

音乐写情绪，特效写已经发生或有条件发生的画面。环境氛围持续，关键特效是某一刻的变化；“也许会爆炸”“他气得像爆炸”不能当作实际爆炸。

章节音乐接受：暧昧、慢热、吃醋、危险、紧张、冷战、秘密、悬疑、背叛、告白、心碎、道歉、接吻、枪火、黑帮、往事、日常、温柔、天亮、终章、静默。不过当前中文导入的章／场音乐映射不完全一致，**新稿优先用紧张、吃醋、悬疑、暧昧、背叛**；其他情绪需要接入人员核对开场曲与后续曲，不能保证只写一个情绪词就处处播放正确。

雨、停电、烛光等氛围要在时间、导语或当前安排里有对应依据。切到晴天或室内恢复供电时，也要更新氛围，不能让画面和文字相反。瞬间特效有条件时写“特效名：触发情境”；不写条件会按进场特效处理，不适合提前揭示事件。

中文特效名以 `api/_scriptparse.js` 的 `FX_NAMES` 为准；常用如“下雨、暴雨雷电、烛光、停电、心跳失控、闪电、重大冲击、收到消息、恢复平静”。完整 id 表保留在文末，供旧 DSL 与直接 JSON 使用。

## 十三、场景图、高光图、照片和开场视频

```text
【主场景图】图名：雨夜前厅 画面描述：画廊前厅，玻璃门外下雨，桌上有登记册，无人物、无文字。
【高光图】
图名：修复台前
画面描述：沈砚停在修复台旁，工具摆在右侧，留出玩家视角的空间。
触发条件：玩家同意来到修复台旁，且实际到达后
【照片】
图名：修好的画角
画面描述：修复后的画角和工具，保持画作及人物外貌一致。
谁发：沈砚
什么时候发：这次修复已经完成，且玩家愿意看时
```

主场景图随场景关联；高光图是实际抵达某个画面后的插图；照片是角色发给玩家的照片，三者不能混成同一个“图已显示”的承诺。每张高光图必须有触发条件，建议每场最多两张。描述未来修复结果的照片只能在修复完成后发。

图名供编辑识别，实际槽位由转换器生成：`bg_c01s01`、`char_c01`、`hl_c01s01_1`、`ph_c01s01_1`、`cover`。不要把“我叫它前厅图”理解成素材已接上；文件路径必须落到作品的素材映射。转换器只产出资料和图片需求清单，不会自动生成或上传图片。

同一角色跨图复用外貌锚点，场景图优先空场，避免把后来没同行的人画死在背景里。推荐竖屏 9:16；941×1672 是既有可用规格，JPG 质量与体积按实际画面检查，不把某个估计 KB 数当硬性标准。生图提示词可由画面描述另转英文，不要求编剧把中文稿改成英文。不要要求画面自带标题、水印或不可读小字。

```text
【封面】画面描述：雨夜画廊的门半掩，暖光落在旧画框上，无标题。
【人物图】沈砚：33岁成年男性，黑发灰眼，深色工作围裙，手指有颜料印，竖屏半身，无文字。
【开场视频】
一句话钩子：你来取画，画框上的编号却变了。
悬念问题：是谁换了它？
镜头脚本：0—3秒，雨滴划过画廊玻璃；3—7秒，凭条与画框编号并置；7—10秒，沈砚放下工具，停在画框旁等你开口。
```

开场视频栏交的是约 10 秒的视频脚本，不是视频文件或播放开关。上线仍需制作、上传并接入实际视频；不要以这条栏目推断“自由故事已自动播放任意视频”。

## 十四、旁白、动作、台词、心声和感官分别怎么写

旁白负责把公开的画面和节奏交代清楚，让玩家看得见人物如何回应、场面停在哪里，并保留下一步参与空间。写作时分别处理作者预写的导语／事件和角色表演之后的动态旁白。

| 类型 | 可以写 | 不能写 |
|---|---|---|
| 角色动作 | 当前角色实际做出的公开动作，保留主体、对象、条件和完成程度 | 把伸手写成已经牵住，把请求写成对方已同意 |
| 角色台词 | 本人所知、所信、所问或所承诺的内容 | 将传闻写成客观真相，替另一人说出未知秘密 |
| 作者导语／事件 | 当前已公开的场面，或到触发条件后真正发生的事件 | 未来谜底、后台目标、未经选择的玩家行为 |
| 新增独立旁白 | 本轮真实送达的公开动作、台词话题、当前地点与实际在场 | 读心、私密感官、未来剧情、选择效果或新增未经表演的动作 |
| 玩家心声 | 玩家自己的私密想法 | 让其他人按共同事实回应 |
| 可选感官 | 非主动的感知和轻微生理反应 | 替玩家发言、移动、答应、原谅或爱上某人 |

### 14.1 作者旁白与动态旁白各承担什么

**作者预写的导语／事件**负责提供当前场面的明确内容。导语写进场时已经公开的环境、位置和局势；事件写符合触发条件后出现的变化。待触发的事件留在事件栏目，不要先在导语里当成已经发生。

**动态独立旁白**在角色实际表演之后补一个镜头。只使用本轮已经送达的公开表演，不负责另演一段剧情、确认选择结果、发放奖励或替角色兑现承诺。作者需要新增门铃、断电、证据到场等事实时，应把它安排成作者事件或角色实际行动，再由旁白承接已发生的画面。

动态镜头不额外创造供角色共享的事实；作者导语、真正触发的事件和角色实际表演仍按其原有事实身份处理。不能把两者都当成可随意添加的气氛文字，也不能把真正发生的作者事件一并当作无效装饰。

**当前独立旁白与新版见闻压缩仍按《零点王冠》试点接入。** 这里补充的是编写要求，不代表其他作品已经默认启用。试点中独立文字带“旁白”标识，由界面负责显示。

### 14.2 叙述视角、主体和信息范围

采用第三人称的旁观镜头，优先写实际在场的角色和已有公开依据的场面。交代“谁在什么位置，做了什么，动作停到哪一步”，让玩家自己判断情绪和意图。

- **人物范围**：只写实际在场的人。计划名单不等于一直在场；离开的人不能在旁白里突然出现、听见私聊或回应秘密。
- **事实范围**：只用当前公开内容。仅进场可取已经展示的当章导语；后续聊天不能反复借旧开场描述已经变化的局势。
- **玩家范围**：玩家公开输入可帮助理解上下文，但当前自动旁白不会将玩家输入直接选成叙述主体。不要替玩家移动、触碰、点头、留下、心动、答应或原谅。
- **认知范围**：角色秘密、心声、私密感官、未来章节、导演意图和选项后果不进入动态旁白。玩家在心里猜到了，也不能改成所有人都知道。
- **环境范围**：沿用已建立的地点和环境；动态镜头不能为文采凭空加雨、改灯色、放音乐，或推断某个道具已经修好。

可写“沈砚把工具放回桌边，停下来等回应”，前提是这套动作确实已经公开表演。不要单凭“他很温柔”的人设描述就补出递伞、擦泪或拥抱。

### 14.3 一段旁白的具体写法

每次聚焦一个镜头，优先使用具体名词和可观察动作。创作建议为 **1—2 个短句、约 20—60 字**；重点在清楚、克制和有画面，不要求为了凑字数扩写。

写作可按“**明确主体＋已有动作／公开变化＋停留位置**”组织。例如：

> 沈砚放下工具，手停在登记册旁。

这句须有相应公开表演作依据。不要把“他犹豫了”单独当成可见动作；可在角色动作里先写停顿、收回手或重新措辞，让玩家从表现中理解。

动作的条件、否定、对象和完成程度必须保留：

| 原有公开表演 | 可用的旁白处理 | 不可改成 |
|---|---|---|
| 凯尔准备伸手 | 凯尔准备伸手。 | 凯尔已经握住对方 |
| 凯尔没有伸手 | 凯尔没有伸手。 | 凯尔伸出手 |
| 如果获准，凯尔才会伸手 | 保留“如果获准”和“才会”，或选择其他镜头 | 凯尔伸手，把人拉近 |
| 凯尔示意侍从压低声音 | 保留凯尔、侍从及“示意”的关系 | 凯尔自己压低了声音 |
| 沈砚说“我会去查登记册” | 沈砚的回应里，提到了登记册。 | 沈砚已经查清记录 |

当前动态实现选择公开来源，由程序保留动作原文的完整限定，或从台词中取原有话题并明确归属；不会直接发布模型自由创作的一段正文。含玩家指代、过长或不适合保留的动作可能改用其他来源或简短衔接，不能承诺任意文艺镜头都能自动写出。

**长度建议与程序上限分开理解。** 动态旁白默认显示上限为 90 字符，实际配置被限制在 30—140 字符之间；超出或不合格时换用其他来源或衔接，不靠截掉动作条件来缩短。作者章节导语仍按导语自身的样式建议编写，不能把所有作者叙事统一理解为硬限 90 字。

旁白一般不承载完整对白，人物需要说的话放在角色台词里。动态镜头提及台词时，只概括已出现的话题并写清是谁提到的，保留“说过、怀疑、承诺”与“已经发生”的区别。

### 14.4 出现时机与重复控制

| 情境 | 作者应怎样安排 |
|---|---|
| 进场 | 导语先交代当前场面；可留一个简短镜头，接到人物实际开口，不重复介绍整部背景 |
| 每场首次选择回应 | 对选择后的实际表演补镜头；选项里的预期后果尚未兑现时不能写成结果 |
| 普通成功交流 | 默认约每 3 轮有一次动态旁白机会，给连续对话留出呼吸 |
| 本轮已有作者旁白或已触发事件 | 已有文字计入本轮，不再机械叠加一段内容相同的动态旁白 |
| 玩家只写心声、角色回复失败或退出收束 | 不强行新增动态旁白，沿用相应内容和收束流程 |

这些是当前试点的调度方式，实际显示还取决于公开来源和状态检查。不要在稿子里写“每三轮必须发生新事件”，也不要让每个角色说完一句都跟一段旁白。下一轮仍在谈同一个话题时，优先留给角色回应，避免反复写同一个动作或旧开场。

动态镜头选择失败、超时或不合格时，可以只显示“沈砚给出了回应”这类基于真实回复者的短衔接。朴素衔接不补写事件，不能为了追求文采编造触碰、证据、动机或情感结论。

### 14.5 编剧具体写在哪些栏目里

中文导入稿继续使用现有栏目，**不要新增不被识别的 `【旁白】` 栏目**。

| 旁白相关内容 | 写在哪里 | 写到什么程度 |
|---|---|---|
| 全剧旁白视角、句式和信息边界 | `【演出风格】` | 用几句规则约束写法，不在这里塞具体事件或秘密 |
| 当前进场画面 | `【章节导语】` | 只写已经公开的环境和局势，不替玩家表态 |
| 尚待发生的公开变化 | `【事件】` | 写事件内容与触发条件，等实际触发再成为事实 |
| 场景内可发展的镜头位置 | `【本章安排】` | 写候选、条件与停留点，不写成已完成的历史 |
| 某角色应如何表现 | `【角色任务】`／`【这一级的表现】` | 约束本人动作和回应，不命令玩家配合 |
| 逐字镜头稿、特殊旁白需求 | 单独的创作说明 | 标明来源、触发条件与适用模式，由接入人员核对；不声称会被中文导入器自动读取 |

可直接参照下面的写法，按本作内容替换。它是一组栏目片段，完整导入结构见样稿：

```text
【演出风格】旁白用第三人称，只写当前公开画面。每次聚焦一个镜头，用短句，保留动作的主体、条件、否定和完成程度。人物台词由人物自己说；旁白不读心、不代写玩家行为，不把承诺或猜测改成事实。已有导语或事件时不再重复补镜头。
【章节导语】雨点沿着画廊玻璃滑下。登记册摊在桌上，沈砚把工具放在一旁，等你开口。
【本章安排】玩家愿意核对时，沈砚可说明登记册的位置并等待确认；不要替玩家翻页或宣布查证成功。旁白只承接本轮已经发生的公开动作，不提前写后来发现的日期。
【角色任务】
沈砚：先答眼前的问题，需要碰玩家物品时先询问。把动作停在请求和等待处，不替玩家表示同意。
【事件】
屋檐的雨声渐轻（触发：当前话题暂告一段落，且本次变化尚未发生）
```

作者导语中的动作属于作者已经建立的开场表演，后续动态镜头只能引用允许的当前公开来源。不要把同一段导语改几个形容词，在后续每轮重新发布。

### 14.6 常见错误怎样改

| 不合适的写法 | 问题 | 可改写方向 |
|---|---|---|
| 你终于懂了他的深情，握住他的手答应留下 | 代定玩家理解、感情、动作和决定 | 只呈现他已经做出的动作，把回应留给玩家 |
| 他早知道换框者，只是故意考验你 | 自添秘密和动机 | “沈砚的回应里，提到了旧画框。”前提是他本轮确实提到 |
| 他的沉默说明他已经原谅你 | 将表现解释成确定的关系结果 | 写已有沉默或动作，原谅由本人表达与后续行为确认 |
| 门突然被踢开，所有人都知道真相了 | 凭空增加事件并让知识瞬间共享 | 门被踢开先有作者事件或实际表演，真相仍按实际披露与见证人处理 |
| 沈砚答应查记录，旁白接着写“记录已经查清” | 将承诺当作完成 | 保留回应的话题，等待实际查证 |
| 再次照抄开场的暴雨与全员站位 | 复用过期场面，可能与环境、在场变化冲突 | 取当前场景和本轮公开表演，没有合适来源就简短衔接 |

### 14.7 与心声、感官和长期记忆怎样衔接

心声保持私密。玩家心里说“我怀疑他在撒谎”，角色只能针对玩家公开表达的言行回应，动态旁白不能替玩家公开这个怀疑，更不能认证他确实撒谎。

感官层需要单独配置，玩家可关闭。用第二人称短句，建议 30 字以内；普通轮可以留空，至少间隔 3 轮。方向服从玩家已经表达的态度，抗拒时不能写成心动。作者可在创作说明中提出“只写雨声、衣料与呼吸，不代定感情”等风格，不要往中文稿添加 `【感官】`。配置及范围见第十七节。

新增动态旁白是镜头补充，不写成以后必须兑现的承诺，不作为额外新增的共同事实。长期记忆保留的事实来自实际公开表演、真实事件、明确边界与程序回执，并按见证人分配；不能因为某句话用了“旁白”标签，就让所有角色自动知道。

## 十五、为长期记忆写清事实

作者不要手写“压缩摘要”来替代内容。把重要变化写成能够辨认来源与状态的事件：

| 情形 | 应保留的性质 |
|---|---|
| “我明天替你查” | 承诺，尚未完成 |
| “我怀疑登记册被换过” | 某人的怀疑，尚未证实 |
| “我试着推门” | 尝试，是否打开等待结果 |
| 明确选择“只做朋友” | 持续边界，不能换章清零 |
| 游戏已经完成并返回 WIN／LOSE／SKIP | 才能据对应结果接剧情 |
| 甲私下说出隐情，乙不在场 | 甲与实际见证人知道，乙不能突然针对它回应 |

新版压缩保留原聊天，只整理模型输入，并按消息当时见证人分配历史。心声、私密感官和新增氛围旁白不变成共同事实。不要把“程序会压缩”理解成角色会自动获得全剧设定。

其他作品可能仍使用原有记忆机制；编剧应始终明确谁何时知道什么，不能只依赖试点机制替错误大纲补救。

## 十六、结局怎么写

```text
【结局名】继续同行
【触发条件】玩家明确愿意继续调查；事件结果和关系意愿分别确认，未选择恋爱可保持朋友关系。
【收束文字】画框的编号还等着核对。沈砚把登记册留在桌上，问你下一次想从哪里查起。

【结局名】提前离开
【触发条件】玩家明确希望结束这段经历。
【收束文字】沈砚收起工具，为你留出离开的路。这幅画可以以后再谈，今晚到这里也可以。
```

每个结局都要有名字、条件和正文；至少一个。建议有“提前离开”，且收束尊重玩家真正意愿。

创作上分别交代事件结果、关系结果、人物变化与此后持续状态。好感高不代表必须恋爱；揭晓真相不代表必须原谅。自由输入到结局要有明确意愿；直接结局选项用第八节的特殊标记映射。

中文 `【触发条件】` 保存的是条件描述，不是任意可执行规则。复杂结局资格需核对实际状态与接入逻辑，不要只凭文案就宣称每条长路线都已能到达。

## 十七、给接入人员的字段对照

编剧优先写中文，接入人员检查转换结果；不要让编剧为了格式猜系统 key。

| 中文稿 | 当前数据入口 |
|---|---|
| 卖点／核心问题 | `hook`、`pitch`／`question` |
| 故事背景／世界规则／演出风格 | `intro`／`world`／`style` |
| 玩家身份、处境、隐情 | `player.role`、`player.pressure`、`player.secret` |
| 相处规则／每章节奏 | `experience.companionRules`／`experience.pacing` |
| 开局认知／可解锁秘密／他人观点 | `cast[].knows`／`cast[].secrets`／`cast[].others` |
| 人物成长／本级表现 | `cast[].arc`／`chapters[].behavior` |
| 时间、眼前的事、导语、对白 | `chapters[].introduction.{time,event,text,lines}` |
| 地点、在场、安排 | `scenes[].place`、`present`、`beat` |
| 角色任务 | `scenes[].actor_payload[角色key]` |
| 邀请与建议 | `scenes[].interaction.{invitation,suggestions}` |
| 正式选项、后果与任务 | `scenes[].choice.options[].{t,effect,actor_payload,state}` |
| 游戏／事件／音乐 | 章 `game[]/events[]/bgm`；转换器也可能生成场景游戏或音乐，需核对 |
| 氛围／条件特效 | `scenes[].fx`／`scenes[].fxPlan.moments` |
| 高光图／照片／开场视频脚本 | `scenes[].highlights`／`photos`／`openingVideo` |

当前主要场景入口是 `beat/actor_payload/interaction/choice`，不要继续把旧 `scenes[].script`、`scenes[].opts` 或 `card98` 当作当前 b98 的通用接口。

中文稿生成的双语对象会将中文同时放入 zh/en，这**不代表英文已翻译完成**。正式出海版本需按总规则本地化，并核对人物声线、术语和场景内容一致。

直接 JSON 的手动推进基础配置：

```json
{
  "experience": {
    "schema": 1,
    "focus": "player",
    "storyIntroduction": true,
    "chapterIntroduction": true,
    "actionView": "thirdPerson",
    "choiceDock": "contextual",
    "allowFreeContinue": true,
    "pacing": {
      "mode": "player-controlled",
      "minExchanges": 12,
      "targetExchanges": 18,
      "allowExplicitSkip": true
    },
    "companionRules": {"zh": "尊重朋友边界；不替玩家决定或行动"}
  },
  "capabilities": {"freeConversation": true, "chapterNavigation": "manual"}

```

以下只作**接入说明**，不能粘到中文导入稿里，也不要求给其他作品批量开启：

- 可选感官：`experience.playerSenses: true`；旧顶层 `playerSenses` 仍有兼容读取。
- 旁白试点：`experience.narration: {schema:1, enabled:true, cooldown:3, maxChars:90, timeoutMs:5000}`。
- 见闻压缩试点：`experience.context: {schema:1, enabled:true}`；新版压缩当前用于 b98，旧 pk／agent97 接入旁白后仍保留其原有上下文机制。
- 直接数据稿的 `arc[]` 只在没有 chapters 时编译为章节；中文稿继续按 `【章序】` 写，不能新增 `【升级台阶】`。

这些对象需**合并到同一份 experience**，不能覆盖掉原有开场、节奏和边界配置。试点实现与核对范围见 [narration-context-pilot.md](../docs/narration-context-pilot.md)，不将试点自动表述为全部作品已上线的能力。

## 十八、旧逐字剧兼容写法

本节保留原规范的 DSL 能力，适用于既有逐字剧入口；不覆盖前面的中文自由故事写法。

```text
⟦ORIENT|bg⟧
⟦CHAR|你|f|24|player|玩家角色|成年访客⟧
⟦CHAR|沈砚|m|33|char_shen|修复师|黑发灰眼，工作围裙⟧
# CHAPTER 1｜雨夜画廊
# SCENE｜画廊前厅
⟦BG|bg_hall|画廊前厅⟧
⟦TIME|21:00⟧
旁白：雨水顺着玻璃门滑下。
沈砚：“你想先看画，还是先坐一会儿？”
# CHOICE｜你怎么回应？
#### A｜先看看画
你：“先看看画。”
#### B｜坐一会儿
你：“我想先歇一下。”
# ·
```

四个结构要件：章节、场景、可解析正文、该入口要求的章末选择。每个 CHOICE 块用 `# ·` 结束，否则后文可能被算进最后一个选项。中文场景头写 `# 场景｜地点`，保留井号；背景和时间标签紧跟所关联的场景。

| 标签 | 用途与写法 |
|---|---|
| `⟦ORIENT\|bg⟧` | bg／bl／gl，与角色卡一致 |
| `⟦CHAR\|名字\|m或f\|年龄\|立绘槽位\|身份\|描述⟧` | 成年人物资料；玩家用“你”明确视角 |
| `⟦BG\|槽位\|地点⟧`／`⟦TIME\|时间⟧` | 给前一个场景关联属性，不等于手动暂停 |
| `⟦FREE\|问题\|建议1\|建议2⟧` | 中段自由输入 |
| `⟦CALL\|角色名\|情境⟧ … ⟦/CALL⟧` | 通话，必须闭合；需要可用的通话服务 |
| `⟦ITEM\|名字\|描述\|🔖⟧` | 道具卡 |
| `⟦OPT\|A\|set:旗子;love:2⟧` | 此入口支持的选项效果，不可照抄成中文特殊标记 |
| `⟦SET\|旗子⟧`／`⟦IF\|旗子⟧ … ⟦ELSE⟧ … ⟦/IF⟧` | 标记与条件分支；条件块闭合 |
| `⟦GOAL\|目标\|English⟧` | 章节目标，不写需要保密的后章答案 |
| `⟦SECRET\|id\|秘密\|knows:谁\|reveal_from:章数⟧`／`⟦REVEAL\|id⟧` | 旧入口的秘密范围和解锁位置，与新版角色 secrets 不同 |
| `⟦BGM\|标签\|风格⟧` | 音乐 cue |
| `⟦FX\|id⟧`／`⟦SFX\|id⟧` | 特效／音效，使用实际存在的 id |
| `⟦CG\|槽位\|说明⟧`／`⟦VIDEO\|槽位\|说明⟧` | 插图／视频，必须另有可访问的素材 |
| `⟦PHOTO\|标题\|说明⟧`／`⟦MG\|游戏id⟧` | 旧照片／游戏卡，不等于中文照片或邀请结果配置 |

CHOICE、FREE、CALL 都可能形成交互等待，不能再写“只有 CALL 才会停”。小游戏的停顿和继续按所用入口实测，不用固定毫秒数或加长句子来保证体验。

玩家台词写“你：”，主要人物写角色卡；旧入口可能根据台词和选择推断玩家，不能让全章只有其他角色表达、导致视角误判。旧心声 `【心理】` 也是这个入口的约定，不能混进中文栏目稿。

旧逐字剧文件只放可播放正文与标签，作品信息、资产表和编辑说明另交。素材槽位要与标签一致，不能只交任意命名的图片。旧入口的标签明细以 [parser.md](parser.md) 及实际解析器为准。

## 十九、交稿前怎样核对

先用下面的命令**只识别、不写入作品**：

```bash
node tools/script-import.mjs scripts/authoring-example.txt --id w_authoring_example
node tools/script-import.mjs 你的稿子.txt --id w_your_work
```

它会使用与后台相同的中文解析器和样式检查，报告人物、章节、场景、选项、结局及素材数量，并指出错误栏目。确认转换结果后，接入人员才用 `--write` 生成作品圣经和图片清单；不要用样稿覆盖已上线作品。

检查已有 JSON 可用：

```bash
node tools/script-style-check.mjs art/official/你的作品.bible.json
```

编辑还需核对这些创作问题，程序通过不等于创作和接入都已完成：

1. 玩家能知道自己是谁、眼前发生什么、角色有什么吸引力、现在可以做什么。
2. 角色按本人知识与关系阶段回应；人物隐情、心声与未来情节没有进入公共导语。
3. 重要选择有可感知后果和后文读取；汇合保留经历，长期路线有转线和退出说明。
4. 尝试、承诺、怀疑和已完成事实分清；朋友边界跨章保留。
5. 游戏三种结果都有继续空间，未发生的结果没有提前写入共同记忆。
6. 图片槽位、触发条件、环境、实际在场人员和素材内容一致。
7. 需程序支持的路线、资源、结局资格与试点开关已单独标明，未接入的不宣称自动生效。
8. 全本容量、对白、本地化、反转与四轴结局继续按上位总规则落实。

内容审核沿用当前系统与作品边界，不将旧文中的有限词表当作完整内容标准，也不能以“没命中某个词”推断描写必然可发布。
