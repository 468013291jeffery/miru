# 发现页：排行 / 挑战 / 赚钻石 / 遇见 —— 现状与设计

2026-11-07 · 基于 main `a129e0d` 代码和本机实测

## 0. 一句话结论

- **排行、挑战、任务三块目前都是本机假数据**：没有服务器表，也没有其他玩家的数据。每个人看到的榜单都不一样，投票只改自己手机上的数字。
- **遇见**已改成按口味匹配（见 §4，本次已实现）。但人选太少：只有 14 个官方男主卡，BL 用户只有 2 个人可滑。
- 要做实，排行和任务都需要后端（新表和新接口），工作量见 §5。

## 1. 排行（`source/src/app7_rank.js`）

### 现状

| 项 | 实际做法 |
|---|---|
| 热度 | 按公式算：角色在列表里排第几（0.952 的 i 次方衰减）+ 按 id 算的 hash + 本周已过小时数自动上涨。**没有任何真实数据**。 |
| 别人的票 | 不存在。「再投 N 票就超过 XX」里的对手热度是公式算出来的。 |
| 你的票 | 存在本机 `S.boost`，只有你自己看得到，换设备或清缓存就没了。 |
| 每日票数 | 本机 `S.vote`，每天 3 票；分享加 1 票；花钻买票（1💎=5 票，5💎=30 票）。**钻石是真扣的，票是假的**。 |
| BL 标签 | 用内置剧的配对表 `BLP` 判断。内置剧 11-06 已全部下线（`app129_catalog.js`），所以 **BL 榜是空的**，而它是默认打开的标签。 |
| 全部 | 只剩 14 个官方男主卡（`art/official/leads.json`）。 |

### 设计

**排什么**：每周角色人气榜（打榜），以官方男主卡为榜单（`ld_*`，作品下线就出榜）。

**热度怎么来**（全部来自服务器）：

```
热度 = 投票数 × 520
     + 本周和 TA 单聊的回合 × 2          ← 需新增：客户端 talk 事件带上角色 id
     + 本周 TA 所在作品读完的章节 × 20    ← 事件表已有 chapter_done
```

第二、三项让冷启动时榜单不是全零，也让"真的有人在玩"能体现出来。不再用公式编造对手。

**票**：

- 登录才能投；游客能看榜。
- 每个账号每天免费 3 票（服务器记），每日任务「投 1 票」从这里验证。
- 花钻买票走同一个接口，扣钻和加票放在一个事务里，带幂等 key。
- 每人每天付费票设上限（建议 100 票），免得一个人把榜买穿。

**页面**：

- 标签按作品的配对（orient）分：「BL / BG / 全部」，**默认打开用户自己的配对**，替代写死的 `BLSET`。
- 每个角色加「应援榜」：本周给 TA 投票最多的前 10 名玩家（显示昵称），这是打榜的社交动力。
- 每周一 00:00 UTC 结算，上周前三名在角色卡上挂「上周冠军」徽章。
- 刷新：榜单接口缓存 60 秒；自己投完票前端先乐观更新。

**后端**：

```sql
CREATE TABLE votes (week DATE, cid TEXT, user_id TEXT, n INT, src TEXT, key TEXT UNIQUE, at TIMESTAMPTZ DEFAULT now());
-- src: free | share | paid
CREATE INDEX ON votes (week, cid);
```

`/api/rank`：
- `GET ?week=&orient=` 返回榜单 `[{cid, heat, votes, rank}]` 加上我本周投了多少、今天还剩几票
- `GET ?cid=&fans=1` 返回应援榜
- `POST {op:'vote', cid, n, key}` 免费票先用；不够时返回 402，前端再弹购买
- `POST {op:'buy', cid, pack, key}` 扣钻并加票

## 2. 挑战（`app2_pages.js` 的 `qBoard`）

### 现状

- 只有带 `w.quest` 的剧才有挑战。这些都是内置剧，已全部下线，所以**挑战标签现在是空页面**。
- 排行榜是 12 个写死的假用户名（`Ken_the_rink`、`Maxiii`……）加上你自己一行。
- 「积分兑换钻石」（500 积分 = 1💎）的积分就来自这个假榜单的公式。

### 设计

- **短期**：没有挑战内容时，发现页不显示「挑战」这个标签，积分兑换也先下掉。
- **中期**：把挑战改成「官方剧结局收集」：
  - 每部官方剧一张卡：结局数（如 4 个）、隐藏结局、全收集人数。
  - 榜单 = 收集结局数 → 首次全收集时间，真实玩家。
  - 数据从已有的事件表来：客户端打出结局时已经在发 `story_end {wid, ending}`（`/api/events`），服务器按 `user_id + wid + ending` 去重计数就行，不需要新的上报接口。注意事件是客户端发的，可以伪造；榜单要防刷，就只认登录用户，并且同一结局之前必须有对应的 `chapter_done` 记录。
  - 奖励：首次打出每个结局 +1💎，全收集 +5💎（走任务系统，见 §3）。

## 3. 赚钻石 / 任务（`app5_money.js` 的 `tasksHTML`）

### 现状

| 任务 | 问题 |
|---|---|
| 关注 Discord / IG / TikTok / YouTube | 点一下就 +1💎，**不打开链接，也不验证** |
| 下载 App | 点一下就 +2💎，只弹一条提示 |
| 分享、邀请好友 | 打开分享面板就算完成，**没有真实邀请归因** |
| 回复动态 | 只显示「去朋友圈回复」，没有入口 |
| 生成图片 | 只有状态，没有入口按钮 |
| 生成视频 | 「即将上线」 |
| 做互动视频 | 按钮跳到「创建群像」，和任务名不符 |
| 投票 | 依赖假榜单 |

钻石先加在本机 `S.keys`，再由 `app68_cloud.js` 同步成服务器的 `wallet earn`，服务器每天上限 80💎（`config.earn_cap`）。所以每个账号每天最多能刷 80💎，但任务本身没有任何验证。

### 设计

**原则**：每个任务的完成条件都由服务器判断，前端只负责展示进度和点「领取」。

**任务定义放后台 config**（`config.tasks`），运营可以改奖励、开关任务，不用发版：

```json
{ "id": "read1", "period": "day", "goal": 1, "reward": 1, "src": "events:chapter_done", "title": {"zh":"读完 1 章","en":"Finish a chapter"} }
```

**任务表（建议第一版）**：

| 周期 | 任务 | 怎么验证 | 奖励 |
|---|---|---|---|
| 每日 | 签到 | 现有 `wallet op:daily` | 3💎 |
| 每日 | 读完 1 章 | 事件表 `chapter_done` 今天 ≥1 | 1💎 |
| 每日 | 和角色聊 10 句 | `/api/longcat` 现在只按天记 token，需加一项回合计数（`usage` 表 kind=`turn`） | 1💎 |
| 每日 | 打榜投 1 票 | `votes` 表（依赖 §1） | 1💎 |
| 每日 | 看广告 | 现有广告逻辑 | 按现有 |
| 每周 | 打出 1 个新结局 | 事件表 `story_end` | 3💎 |
| 每周 | 连续签到 7 天 | `user_days` 表 | 5💎 |
| 一次性 | 设定我的人设 | 存档 `persona` | 2💎 |
| 一次性 | 读完第一部剧的第 1 章 | 事件表 | 2💎 |
| 一次性 | 邀请 1 位好友注册 | 注册时记录邀请人（`ref` 参数） | 5💎（双方各得） |
| 一次性 | 发布角色 / 作品并通过审核 | `works` 表 author + status=live | 3💎 |

**下掉或改掉的**：

- 关注社媒：真打开对应链接，奖励降到 0 或做成纯入口（无法验证）。
- 下载 App：改成「在 App 里登录一次」，用请求来源验证。
- 分享：不再按"打开面板"给奖励，只有通过分享链接带来新注册时才给（并入邀请）。
- 回复动态、生成视频、做互动视频：没有入口前先隐藏。

**后端**：

- `GET /api/tasks` 返回 `[{id, progress, goal, claimable, claimed}]`，进度在服务器算。
- `POST /api/tasks {op:'claim', id}` 校验通过后用 `wallet` 的 `apply()` 加钻，幂等 key = `task:<uid>:<id>:<周期>`，仍受 `earn_cap` 限制。
- 前端 `taskClaimDay` / `taskClaimOnce` 不再直接改 `S.keys`。

## 4. 遇见（`app96_social.js` ⑥）—— 本次已实现

### 原来

所有角色按日期随机洗牌，看完一轮清空重来，和口味无关。

### 现在

1. **过滤**（不合适的不出现）：
   - 只从官方角色卡里挑（`C` 表）。打开官方剧后装进来的剧中角色和男主卡是同一个人，不重复出现；玩家自己扮演的角色和自己捏的角色也不出现。
   - 配对和「不想看」沿用口味设置（`orOK`）。
   - 尺度不超过用户选的档位。
   - 已经在聊的人不再出现。
   - 左滑过的人 14 天内不出现。
2. **打分排序**：
   - 口味标签命中，每命中一个 +12。
   - 滑卡学到的偏好：右滑给 TA 的作品标签加分，左滑减分，旧分逐渐衰减。
   - 玩过 TA 的剧 +8。
   - 新角色 +4。
   - 再加少量热度和每日随机。
3. **每天一副固定的牌**：同一天关掉再打开顺序不变。每 5 张插 1 张口味之外的「换换口味」，免得越推越窄。
4. **卡片**：显示「匹配 xx%」和推荐理由，比如「你喜欢的：奇幻言情 · 慢热」「你玩过《八位王子都想娶我》」。
5. **看完了**：显示「合适的人你都见过了」和「调整口味」按钮，改完口味当场重新算。免费次数用完、但还有合适的人时，才显示「再滑 30 次 · 2💎」。原来没人可看也会让人付钱。
6. **埋点**：`meet_open`、`meet_swipe`（角色、左滑/右滑/超级喜欢、匹配度、是否换口味卡），后续可以用来算每个角色的右滑率。

顺带修了数据：`leads.json` 里《未读的选择》（BL）缺 `orient`，被当成 BG，BL 用户看不到威廉和亚历克斯。已补上 `orient: "bl"` 和标签。

### 下一步

- **人选太少**：14 张卡里 BG 12 张、BL 2 张。要把每部官方剧的主要角色都做成卡，写进 `leads.json`。这比算法重要。
- 有了 `meet_swipe` 数据后，可以把「全站右滑率」加进打分（服务器算好，随 leads.json 下发）。

## 5. 实现情况（2026-11-07）

已完成，未上线：

- **遇见**：§4 全部。
- **打榜后端**：`api/_board.js`，入口借 `/api/wallet?r=rank`，不新增 Vercel 函数，也不改 `api/_lib.js`（服务器上 `_lib.js` 有本地适配版，改了会让部署停下）。`votes` 表第一次请求时自动建。
  - 热度 = 票数 × 520 + 单聊回合 × 20（每人每周封顶 50）+ 作品读完章节 × 10。
  - 免费票 3 张/天（`config.vote_free_daily`），分享 +1；买票 1💎=5、5💎=30，每天上限 100（`config.vote_paid_daily_cap`）。重复的 key 不会重复计票、扣钻。
- **任务后端**：`/api/wallet?r=tasks`，`task_claims` 表。默认任务见 `api/_board.js` 的 `TASKS`，后台 `config.tasks` 可以整张替换。领取和 `wallet earn` 共用 `earn_cap`。
  - 第一版任务：读完 1 章、聊 10 句、投 1 票（每日）；打出 1 个结局、本周来 5 天（每周）；新手读完第一章（注册 14 天内）、发布作品并通过审核（一次性）。
  - 没做：邀请归因。分享、邀请、关注社媒、下载 App 这几项不再给钻。
- **前端**：`app7_rank.js` 整个改成读服务器，标签默认打开自己的配对，加了应援榜和上周冠军。赚钻石页改成服务器任务。各处 `taskClaimDay / taskClaimOnce` 不再在本机加钻。
- **埋点**：`talk` 事件带上角色 id（`cid`）；剧情事件带上社区作品 id（`cw`）。
- **没动**：签到和看广告还是原来的本机机制，仍通过 `wallet earn` 同步。`walletDiff` 允许客户端每天自报最多 80💎 的口子还在，要堵就得把签到、广告也搬到服务器。
- **测试**：后端在本地 PGlite（真 Postgres）上跑过一整套测试；页面在浏览器里接本地接口实测了投票、买票、应援榜、任务领取和断网状态。线上数据库还没跑过。
