## 三、做成的形状（与当初的设计稿差在哪）

设计稿写的是**两个对象**：`MSGKIND.add(类型, 渲染器)` + 单独的 `MSGWRAP.add(...)`。
落地时改成了一个注册表、用 `cls` 字段分三类 —— 理由只有一条：
**这三类必须在同一个地方、按安装顺序排成一条链**。拆成两个对象，
就多出一个要保持同步的东西，而且仍然回答不了「这条链长什么样、谁包着谁」。

```js
MSGKIND.inline('app42_decline.js', ['declined'], function(m, i, th, next){ …; return next(m,i,th) });
MSGKIND.post  ('app98_story.js',   function(h, m, i, th){ …; return h });     // 返回字符串 = 改过了
MSGKIND.wrap  ('app34_hints.js',   function(m, i, th){ …; return m2 });       // 返回对象 = 换入参
```

**仍然是原位安装**（顺序一字不改）：后处理层必须看到内层渲染结果，整体挪到最外层会让它看不到消息。
分发顺序读作 `wrap → kind → post` 是**结果**，不是被强制的：链上每一层自己决定要不要 `next()`。

| 2.5 | 写「消息渲染快照」对拍工具 | 迁移前后**逐字节**一致 | ✅ `tools/render-snapshot.mjs` |
| 2.6 | 写「每层活着吗」探针（计划外，现实逼出来的） | 每条 `fires` 必须命中、每条 `silent` 必须不动、对照不许被扰动 | ✅ `tools/msgkind-probe.mjs`（26 条） |
| 3 | 搬**条件型**（`say` / `act` / `think` / `box`） | 两张表同时绿 + 变异各红一次 | ✅ 含 `app16` 那处拆成 post+kind 两层 |
| 4 | 后处理与改入参两类独立立表 | 同上 | ✅ 6 `post` + 2 `wrap`，各有一条命中探针 |

**做完之后的判据证据**（不是"看着对"）：**20 种**消息逐字节一致 · 18 层里 17 层被证明活着 + 1 层登记为已知死（22 条命中判据）
· 1 层显式登记为已知死（`app18`，附原因）· 两个变异体分别红在 `#mquick` 的命中线与
`xmoney` 的接力线上（后者红了 3 条，含 `mustNot` 与 `!sealed` 两条新臂）。

**新增的第 2.6 步（原计划没有，现实逼出来的）**：`tools/msgkind-probe.mjs` ——
对拍只证「结构没变」，证不了「这一层还活着」。实测代价见 `ARCHITECTURE.md` §7.7 第 6 条：

存成文本；迁移前后各跑一次，**逐字节 diff**。没有这个对拍，第 3 步就是在猜。

## 五、当时的顾虑与事后对照（实测）

原来写着「今晚不动」的三条理由，现在可以逐条结账：

| 当时的顾虑 | 事后 |
|---|---|
| 这是每种消息都走的路径，一次搬错 = 全站变形 | 成立，但**批量搬是安全的**：判据够硬（逐字节 + 每层命中）时，第 3 步那 10 层是一次搬完的，19 种消息始终一致 —— 「一层一改」在**判据不清楚**时才是必需的 |

| 形状有三种，混着搬会出事故 | 成立。拆成三类各自登记之后，每一类只有一个问题要回答 |
| （新增）静态扫源码就能画出认领图 | **不成立**：`app24` 认领 `xmoney` 被漏记（条件写成取反）。认领是运行期事实 ⇒ `--graph` 改读运行期 |

## 六、给下一个执行者的四句话

1. **先造对拍工具，再动一行代码。** 判据是「同一批样例前后 HTML 逐字节相同」，不是"看着还行"。
2. **表里要能表达"条件"**：条件写进各自的渲染器里，**不要**写成分发器的一部分 ——
   分发器一旦开始懂业务条件，它就变成了第 21 层包装。
3. **对拍之外还要一条"命中"读数。** 一个层可以既不改结构、又什么都没做（选择器失效、条件是死的）——
   那在逐字节对拍里和无害是一模一样的。`msgkind-probe` 就是问这句话的地方；
   「已知死」必须显式登记成会红的断言，否则它会安静地烂下去。
4. **"多层认领"要写成双向断言，别写成注释。** 外层答了 / 内层必须没跑，
   两边都红得起，才叫这条链是可读的；只查一边，顺序反了照样绿。
